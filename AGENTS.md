# Инструкция для Codex — Elementra Dungeons

Ты работаешь над **отдельным модульным плагином** системы данжей Elementra. Это частная кодовая база проекта; не переизобретай общую концепцию сервера. Общайся и оформляй документацию на русском языке; имена классов, API и кода — на английском.

## Приоритет источников

- `docs/reference/concept.md` (master концепция 3.1.1) и `docs/reference/technical.md` (master ТЗ 3.1.1) определяют утверждённые требования.
- `docs/reference/roadmap.md` — статус и ограничения ЗБТ.
- `docs/dungeons.md` — **неутверждённый проект** детализации 0.1; предложения с пометками `[ПРЕДЛОЖЕНИЕ]` и `[ОТКРЫТО]` не превращать в обязательную механику без решения владельца.
- `docs/decisions.md` — журнал открытых решений.

При изменениях внимательно читай соответствующие разделы и сохраняй принятые решения. Если документы расходятся — описывай конфликт в предложении/PR, не подменяй его собственным выбором.

## Целевой стек

- Minecraft Java Edition, Purpur/Paper 26.2, Java 25.
- Никаких обязательных клиентских модов.
- Сборка Gradle; проверяй реальную версию API и координаты зависимости, не выдумывай артефакты и не утверждай сборку без фактического запуска.
- `plugin.yml` или другой поддерживаемый дескриптор плагина должен быть корректно установлен и проверен при реализации.

## Игровой контракт

- Данжи физические и неинстансовые; существуют в общем мире.
- `Dungeon Template` (постоянная локация) и `Dungeon Run`/`Attempt ID` (прохождение) — разные сущности.
- Одновременно один активный забег на физический данж; защита от гонок.
- Комнаты, триггеры, двери и взаимодействия проверяются на сервере.
- Разрешены одиночное и групповое прохождения; FourNations не обязателен для победы.
- Награды не зависят исключительно от последнего удара, выдаются устойчиво и не дублируются.
- Нужны защита от строительства и обходов, кулдауны, восстановление, корректное завершение при рестарте.
- Процедурная генерация, рейтинги, матчмейкинг и случайные модификаторы не входят в MVP.

## Архитектура и безопасность

- Держи отдельные границы: dungeon lifecycle, regions/protection, rooms/triggers, participants, mobs/boss integration, rewards, persistence/reset, admin diagnostics.
- Избегай прямого доступа к чужим БД: межмодульное взаимодействие только через подтверждённые публичные сервисы/API и их устойчивые контракты.
- Никогда не блокируй главный серверный поток синхронной работой с БД. Изменение мира/Paper API — на соответствующем серверном потоке.
- Уникальные идентификаторы для попыток и денежных/предметных операций; идемпотентность и восстановление после сбоев.
- При сбое закрывай данж безопасно (`ERROR`/восстановление), без дюпов и 'выдачи на удачу'.
- Не загружай удалённые чанки только ради спавна/сохранения попытки.
- Ограничивай число сущностей, частиц и задач; не сканируй все данжи каждый тик.
- Перезапуск сервера и восстановление состояния — обязательные сценарии тестирования.
- Права администрации разграничены; все мутирующие действия записываются в аудит.

## Обязательная отчётность после каждой задачи

Указывай независимо следующие статусы: `SPECIFIED`, `SOURCE_READY`, `COMPILED`, `TESTED`, `INTEGRATED`, `RUNTIME_VERIFIED`, `RELEASE_READY`. Повышай статус только по факту испытания и приводя конкретные команды и результаты; не путай тестовый стенд с production.

При изменении игровых правил обновляй связанное место в документации, не удаляя несвязанные разделы. Для спорных решений фиксируй предложения и альтернативы, не выдавая их за утверждённый баланс.
